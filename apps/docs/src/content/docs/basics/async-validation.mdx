Any validator that returns a promise is treated as async automatically. In practice, you rarely want to hit your server on invalid input, so the standard pattern is to chain cheap local checks in front of a debounced server check with `pipe`.

Try typing a short name, an invalid symbol, and then `ada` into the demo below.

<Demo name="async-validation/username" />

```ts
const account = forms.define({
  defaultValues: { username: "" },
  validate: {
    fields: fieldValidators({
      username: validateOn(
        pipe(
          (name) => (name.length < 3 ? { message: "Use at least 3 characters." } : undefined),
          (name) => (/^[a-z0-9_]+$/i.test(name) ? undefined : { message: "Use letters, digits and underscores." }),
          debounced(
            async (name, { signal }) =>
              (await isTaken(name, signal)) ? { message: "That name is taken." } : undefined,
            400,
          ),
        ),
        "input",
      ),
    }),
  },
  show: "always",
});
```

Here is how those pieces fit together:
- **`pipe(...checks)`** runs each check in order and stops at the first error. While either local check fails, the pipe stays synchronous: the debounced server check never starts, and `field.validating` stays `false`.
- **`debounced(check, 400)`** waits for a 400 ms pause in typing before calling `isTaken`.
- **`validateOn(..., "input")`** runs the whole pipe from the first keystroke instead of waiting for the first blur.
- **`show: "always"`** shows errors while the user is still typing (by default, errors wait until blur; see [Deciding when to show errors](./validation#deciding-when-to-show-errors)).

## How `pipe` works

A check inside `pipe` passes when it returns `undefined`, `null`, an empty list, an empty `ErrorMap`, or a schema result with no issues. You can mix functions, Standard Schemas, and wrapped checks in any order, and schema issues still flow through `mapError`.

Wrap the whole `pipe` in `validateOn` to control when it triggers. If any check inside a `pipe` is wrapped in `recheckOnSubmit`, the entire pipe re-runs on submit.

## Race conditions

If the user types again while a request is still in flight, the previous run's `AbortSignal` aborts and its result is ignored, so a slow response never overwrites a newer one. Pass `signal` straight to `fetch`. The signal also aborts automatically if the field is reset or the validator is removed.

## Showing a loading state

While an async check is running, `field.validating` is `true` on that field (and `state.validating` is `true` on the form), so you can show inline status right next to the input:

```tsx
<form.Field name="username">
  {(field) => (
    <>
      <input {...inputProps(field)} />
      {field.validating ? <p role="status">Checking...</p> : null}
    </>
  )}
</form.Field>
```

## What happens on submit

When the user submits, any pending debounce is skipped immediately, even inside a `pipe` that hasn't reached the debounced step yet. If an async validator is already in flight, submit waits for it to finish and only continues if it passed.

Checks whose value hasn't changed since the last run don't re-run unnecessarily. If a check can go stale on the server (like username availability), wrap it in `recheckOnSubmit` so it always runs fresh when the user submits:

```ts
username: recheckOnSubmit(validateOn(pipe(checkLength, debounced(checkName, 400)), "input")),
```
