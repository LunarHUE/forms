Any validator that returns a promise is automatically treated as async—no extra flags or setup needed. Try typing `ada` into the demo below to see debounced server validation in action.

<Demo name="async-validation/username" />

```ts
const account = forms.define({
  defaultValues: { username: "" },
  validate: {
    fields: fieldValidators({
      username: validateOn(
        debounced(
          async (name, { signal }) =>
            (await isTaken(name, signal)) ? { message: "That name is taken." } : undefined,
          400,
        ),
        "input",
      ),
    }),
  },
  show: "always",
});
```

Notice how the pieces stack cleanly:
- **`debounced(check, 400)`** waits until the user pauses typing for 400ms before firing the request.
- **`validateOn(..., "input")`** kicks off validation from the first keystroke instead of waiting for the first blur.
- **`show: "always"`** surfaces the error immediately while the user is still in the field (by default, errors wait until blur—see [Showing errors](./validation#deciding-when-to-show-errors)).

Because `debounced` and `validateOn` both return standard validators, you can nest them in either order and use them anywhere—including in a `validate` prop.

## Running cheap checks first

There's no reason to hit your server if the username is only two characters long or contains invalid symbols. Wrap your checks in `pipe(...checks)` to run them sequentially and stop at the very first failure:

```ts
username: pipe(
  (name) => (name.length < 3 ? { message: "Use at least 3 characters." } : undefined),
  (name) => (/^[a-z0-9_]+$/i.test(name) ? undefined : { message: "Use letters, digits and underscores." }),
  debounced(async (name, { signal }) => ((await isTaken(name, signal)) ? { message: "That name is taken." } : undefined), 400),
),
```

While either of the two format rules fails, the pipe stays completely synchronous—the debounced server check never even starts, and `field.validating` stays `false`. Only once the username looks valid does it wait for a pause and ask the server.

A check inside `pipe` counts as passing when it returns `undefined`, `null`, an empty list, an empty `ErrorMap`, or a schema result with no issues. You can freely mix functions, Standard Schemas, and wrapped checks (schema issues still flow through `mapError`). To control when the entire pipe runs, wrap the `pipe` itself in `validateOn`. If any step inside the pipe is wrapped in `recheckOnSubmit`, the whole pipe re-runs on submit.

## Race conditions are handled for you

If the user keeps typing while a request is still in flight, the previous run's `AbortSignal` is aborted and its result is ignored—so a slow response can never overwrite a newer one. Pass `signal` straight to `fetch`. The signal also aborts automatically if the field is reset or the validator is removed.

## Showing a loading state

While an async check is running, `field.validating` is `true` on that field (and `state.validating` is `true` on the form as a whole), making it easy to show inline feedback right next to the input:

```tsx
<form.Field name="username">
  {(field) => (
    <>
      <input {...inputProps(field)} />
      {field.validating ? <p role="status">Checking...</p> : null}
    </>
  )}
</form.Field>
```

## What happens on submit

When the user submits, any pending debounce is bypassed immediately—even inside a `pipe` that hasn't reached the debounced step yet. If an async validator is already in flight, submit waits for it to settle and only proceeds if it passes.

Checks whose value hasn't changed since the last run aren't re-run unnecessarily. If a check can go stale on the server (like username availability), wrap it in `recheckOnSubmit` so it always runs fresh when the user hits submit:

```ts
username: recheckOnSubmit(validateOn(debounced(checkName, 400), "input")),
```
