Every form can validate, with no plugin installed. Give it validators in
`define`, add one from a component, or call `validate()` yourself. Try `ada`
as the username to see the async check.

## Field validators

`validate.fields` is shaped like the value. Give a field a function that
returns an error, or `undefined` when the value passes. A Standard Schema for
that one field works too:

```ts
const signUp = forms.define({
  defaultValues: { username: "", email: "" },
  validate: {
    fields: {
      username: (name) =>
        name === "admin" ? { message: "That name is reserved." } : undefined,
    },
  },
});
```

`validate.form` takes one validator for the whole value. It returns
`{ fields: { "address.city": error } }`, keyed by dotted field name, and each
error lands on its field. `form` in the same object holds errors for the form
as a whole. At an array, a one-element tuple applies its entry to every item:
`{ lines: [{ sku: checkSku }] }`.

A component can add a validator too. The `validate` prop on `Field` or a
registered component, `useValidator` in React and `createValidator` in Solid
add one while the component is mounted. `handle.registerValidator(validator)` adds one from
anywhere and returns the function that removes it.

## A schema

`schema` validates the whole form and types it, so you write the shape once.
It needs the schema plugin for its library, `zod()` or `valibot()` from
`@lunarhue/forms-schema`. Without it, the compiler names the plugin to add.

```ts
import { zod } from "@lunarhue/forms-schema/zod";
import { z } from "zod";

const forms = createForms({ plugins: [zod()] });

const signUp = forms.define({
  schema: z.object({
    username: z.string().min(3, "Use at least 3 characters."),
    email: z.email("Enter a valid email."),
  }),
  onSubmit: (value) => value,
});
```

The schema plugin also gives the form its starting values. [Schemas](../plugins/schemas)
covers both plugins and how to support another library. A definition can have
a schema and `validate.fields` at once, and both run.

## Async

A validator that returns a promise is async. While it runs, `field.validating`
is true.

```ts
username: {
  validate: async (name, { signal }) =>
    (await isTaken(name, signal))
      ? { message: "That name is taken." }
      : undefined,
  debounce: 400,
},
```

When the user types again, the older run's `signal` aborts and its result is
dropped, so a slow answer never wins over a newer one. Pass the signal to
`fetch`. `debounce` waits for a pause in typing. Submit skips the wait, and a
submit waits for a check that is still running and goes on only if it passed.

## When validators run

A validator first runs on the field's first blur. Set `validate` on
`createForms` to `"input"`, `"blur"` or `"submit"` to change that for every
form, `validate.on` in a definition for one form, or `on` on one validator.
After its first run, a validator runs on every input.

`field.validate()` runs a field's validators now and resolves true when it is
valid. `store.validate()` runs every validator in the form. A submit runs
them all and stops if any field has an error.

## Errors

Errors show once a field is touched or the form submitted. `show` on
`createForms` or a definition changes that: `"always"`, `"touched"`,
`"submitted"`, `"touched-or-submitted"`, or a function. `field.errors` has
every error and `field.shownErrors` only the ones to show now.

`field.invalid` is true when the field has any error. That includes errors
you set yourself with `setErrors`, such as a server's answer. Those also sit
in `field.userErrors`, and they don't block a submit: the form's `valid`
only counts validation errors. The next user edit clears them.
[Submit](./submit) shows how to put server errors on fields.

`errors` lists validation errors in a fixed order: the schema's, then the
form validator's, then field validators' in the order they were added. To
tell them apart, pass a handle to `errorsByKind`. It returns
`{ schema, form, field }`, each a list of errors, and leaves out what
`setErrors` set. A thrown validator's error goes under that validator's
kind. It reads once, so call it again when the field's `errors` change:

```ts framework=react
import { errorsByKind } from "@lunarhue/forms-react";

const { schema, form, field } = errorsByKind(store.root.at("email"));
```

```ts framework=solid
import { errorsByKind } from "@lunarhue/forms-solid";

const { schema, form, field } = errorsByKind(store.root.at("email"));
```

A form that never calls it doesn't ship it.
