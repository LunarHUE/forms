If you already validate data with Zod, Valibot, ArkType, or any other [Standard Schema](https://standardschema.dev) library, you can plug your schema straight into a form definition. Core reads Standard Schema natively, so you don't need a plugin just to validate.

Try typing `admin` as the username in the demo below to see schema rules and custom field validators working side by side.

## Using a schema for the whole form

Pass your schema to `schema` inside `forms.define()`. It both validates the form and drives its TypeScript types. Without a schema plugin installed, you still provide a complete `defaultValues` object:

```ts
import { z } from "zod";

const SignUp = z.object({
  username: z.string().min(3, "Use at least 3 characters."),
  email: z.email("Enter a valid email."),
});

const signUp = forms.define({
  schema: SignUp,
  defaultValues: { username: "", email: "" },
  onSubmit: (value) => `Signed up ${value.username}.`,
});
```

When the user submits, `onSubmit` only runs if the schema passes, and it receives the schema's **parsed output** with any `.transform()` or coercion already applied. If you ever need the raw form values before transformation, they're available on `ctx.input`.

## Using a schema for a single field

You don't have to use a schema for the whole form. Any Standard Schema whose input matches a field's type can stand in for a validator function inside `fieldValidators`, `pipe`, or a `validate` prop:

```ts
const signUp = forms.define({
  defaultValues: { username: "", email: "" },
  validate: { fields: fieldValidators({ email: z.email("Enter a valid email.") }) },
});
```

When you validate individual fields this way, the form's overall type still comes from `defaultValues`.

## Mixing a schema with custom validators

Schemas work well for structural rules, while custom validators handle dynamic or async checks (like hitting an API). You can use both on the same form and they run together automatically:

```ts
const signUp = forms.define({
  schema: SignUp,
  defaultValues: { username: "", email: "" },
  validate: {
    fields: fieldValidators({
      username: (name) => (name === "admin" ? { message: "That name is reserved." } : undefined),
    }),
  },
});
```

When multiple sources report errors on the same field, `field.errors` keeps them in order: schema errors first, followed by form validator errors, then field validator errors.

## Skipping repetitive `defaultValues`

Writing out `defaultValues` by hand gets repetitive on large forms when your schema already describes every field. When you want the schema to generate starting values for you, add one of the [schema plugins](../plugins/schemas) to make `defaultValues` optional.
