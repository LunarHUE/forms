Plugins can build on top of each other and inspect what else is installed without tight coupling.

## Declaring plugin dependencies with `requires`

If your plugin reads state or calls APIs from another plugin, list that plugin's factory in `requires`:

```ts
import { definePlugin, dirty } from "@lunarhue/forms-core/plugins";

const autosave = definePlugin({
  name: "autosave",
  requires: () => [dirty],
  setup: (ctx, wait: number) => ({
    when: "deferred",
    onWrite() {
      // ctx.store.changes() is typed because autosave requires dirty.
      if (ctx.store.changes().length > 0) schedule(wait);
    },
  }),
});
```

`requires` declares a requirement rather than auto-installing the dependency. If someone installs `autosave()` without `dirty()`, TypeScript stops them with `Add dirty() to the plugins: autosave requires it`, and untyped code throws [`plugins:missing`](/errors#core:plugins:missing) in development.

Declaring `requires` gives you three things at once:
- **Typed `ctx.store` and `ctx.plugins`:** requiring `dirty` unlocks `ctx.store.changes()` and dirty flags; requiring `arrays` unlocks array commands like `push`; and required plugins' APIs appear on `ctx.plugins`.
- **Guaranteed hook order:** your plugin's hooks always run *after* the plugins it requires (this is the only ordering mechanism, keeping execution predictable).
- **Cycle detection:** circular dependencies fail fast with [`plugins:cycle`](/errors#core:plugins:cycle).

## Inspecting installed plugins and parts

Sometimes a plugin wants to back off when another plugin or part is already handling a field, for example a generic formatter yielding to a field-specific mask.

- **`ctx.installed`** lists every installed plugin on the store in hook execution order.
- **`ctx.parts(path)`** returns the parts attached at or above `path` in hook order as `{ name, path }` entries (standalone parts without a plugin use the name `"part"`).
