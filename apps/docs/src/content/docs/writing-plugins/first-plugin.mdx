When none of the built-in plugins fits what your app needs, you can write your own. Suppose pasted text keeps introducing extra spaces into your forms, and you want to trim and collapse them across every string field as soon as the user leaves an input. Try typing extra spaces below and tabbing or clicking out.

## A part or a plugin?

Before reaching for `definePlugin`, check whether a standalone [part](./parts) is enough. If the behavior only targets specific field types, holds no internal state, and doesn't need to expose a form-level API, `masked` from `/text` or `transform`, `text`, and `observe` from `/plugins` work with no plugin installation:

```ts
import { masked } from "@lunarhue/forms-core/text";

export const NoteField = defineField(
  NoteInput,
  masked({ clean: (value) => value.replace(/ {2,}/g, " "), display: (value) => value }),
);
```

Write a plugin when the behavior covers the whole form (like cleaning up every string field on blur), needs field or form meta, exposes a `form.plugins.<name>` API, or depends on another plugin.

## Creating a plugin with `definePlugin`

Import `definePlugin` from `@lunarhue/forms-core/plugins` (or your adapter's `/plugins` entry). It returns a factory function that produces a plugin instance whenever you call it:

```ts
import { definePlugin } from "@lunarhue/forms-core/plugins";

export const collapseSpaces = definePlugin({
  name: "collapseSpaces",
  setup: (ctx) => ({
    onBlur(path) {
      const value = ctx.store.getSnapshot(path).value;
      if (typeof value !== "string") return;
      const clean = value.trim().replace(/ {2,}/g, " ");
      if (clean !== value) {
        ctx.write(() => ctx.store.fieldAt(path)?.setValue(clean, { edited: false }));
      }
    },
  }),
});

const forms = createForms({ plugins: [collapseSpaces()] });
```

`setup` runs once per store and returns form-wide hooks. Here, `onBlur(path)` fires every time the user leaves a field (not just the first blur that sets `touched`), reads the current value, and writes the cleaned string back via `ctx.write(...)`. A plugin can also define a `part` hook (which runs once per attached [part](./parts) and returns hooks scoped to that path), or both.

Why `onBlur` instead of rewriting strings in `beforeWrite`? Because `beforeWrite` runs on every keystroke, and changing a string's length mid-edit without caret tracking jumps the cursor to the end of the input (for example, pressing Space in the middle of `"Test |input"` would jump to `"Test input|"`). Form-wide text cleanup belongs on `onBlur` (or `beforeSubmit`), while live per-keystroke rewriting belongs on a field part with `masked` or `afterInput` + `replaceText` (see [Masks](../plugins/masks#caret) and [Parts](./parts)).

Need plugin options? Add a typed second parameter to `setup`, and the generated factory accepts the same argument:

```ts
export const squeeze = definePlugin({
  name: "squeeze",
  setup: (ctx, max: number) => ({
    onBlur(path) {
      const value = ctx.store.getSnapshot(path).value;
      if (typeof value !== "string") return;
      const clean = value.replace(/ +/g, (run) => run.slice(0, max));
      if (clean !== value) {
        ctx.write(() => ctx.store.fieldAt(path)?.setValue(clean, { edited: false }));
      }
    },
  }),
});

createForms({ plugins: [squeeze(2)] });
```

Make the parameter optional to make options optional; omit it for a zero-argument factory.

## How `setup` and `onActive` work (and SSR)

`setup` runs synchronously when the store is created, on both the server and the client, before anything subscribes. Any values, flags, or meta it sets become part of the store's initial state:

- **SSR-safe:** server HTML and the first client render see the exact same state, so hydration happens in one pass (this is how [`rules`](../plugins/rules) renders `disabled` and `hidden` fields on the server).
- **Quiet startup:** setup produces no write records, triggers no `onWrite` hooks, and schedules no deferred or idle timers, so a server-side store that's never mutated never leaks timers.
- **Baseline stays put:** values written in `setup` don't move the baseline (they look dirty against `defaultValues`). To override the initial value without marking the form dirty, use [`initialValue`](./submit#starting-values) instead.

Because `setup` runs on the server, keep it deterministic. Anything that touches browser APIs like `localStorage` belongs in `onActive`, which runs only when the store gets its first subscriber and therefore never runs during SSR. (That is how [`persist`](../plugins/persist) restores drafts.)

## Intercepting and making writes

`beforeWrite` runs in plugin order before each value write, returning either the value to store or `refuse` to cancel the write. Whole-object writes pass through `setup` hooks once at the object's path, while part hooks receive the write walked down to their specific path (so a `masked` part on `phone` still cleans values during a whole-form reset).

New rows added via `push` or `insert` also run through `beforeWrite` at the new row's path (with `before: undefined`). The row already has its key assigned; return a replacement row, or return `refuse` to remove it immediately. Forms without any `beforeWrite` plugin skip this work completely.

When a plugin writes values itself, wrap the writes in `ctx.write(...)`. Queued plugin writes run after the current round finishes, re-running active validators once at the end (without restarting unrelated async checks), and are tagged with `cause: { plugin: name }`. If your plugin is rebasing external data onto the baseline (like [`rebase`](../plugins/rebase)), pass `"rebase"` as the second argument: `ctx.write(fn, "rebase")`. Those are the only two causes available to plugins (`"user"` and `"reset"` belong to the form), letting other plugins decide how to react (for example, `masked` skips rebases).

## Writing after an `await`

Once a hook hits an `await`, the synchronous hook round has already ended, so writing directly to `ctx.store` afterwards looks like a regular user edit (marking the field `edited` and pushing an undo step onto `history`). Always wrap post-`await` writes in `ctx.write` and pass `{ edited: false }` when the value isn't user input:

```ts
async beforeSubmit() {
  const token = await fetchToken();
  // Wrong: treated as a user edit and recorded in undo history.
  ctx.store.root.at("token").setValue(token);
  // Right: plugin write, not marked edited.
  ctx.write(() => ctx.store.root.at("token").setValue(token, { edited: false }));
}
```

## Reacting to blur with `onBlur`

`onBlur(path)` fires on every `handleBlur` call, not just the first blur that sets `touched`, and receives the field's stable path. It runs inside the blur's batch, right after `touched` is updated and blur validators finish, so any `ctx.write(...)` you do inside it lands in the same batch and notifies listeners once:

```ts
const trim = definePlugin({
  name: "trim",
  setup: (ctx) => ({
    onBlur(path) {
      const value = ctx.store.getSnapshot(path).value;
      if (typeof value === "string" && value !== value.trim()) {
        ctx.write(() => ctx.store.fieldAt(path)?.setValue(value.trim(), { edited: false }));
      }
    },
  }),
});
```

Programmatic `setTouched(true)` calls and blurs on removed fields don't trigger `onBlur`. For parts, `onBlur` only fires for blurs at or underneath the part's path.
