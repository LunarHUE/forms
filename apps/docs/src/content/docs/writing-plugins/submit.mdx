Plugins can participate at both ends of a form's lifecycle: supplying the initial value before the store starts, gating a submit before `onSubmit` runs, and reacting once a submit finishes.

## Gating or refusing a submit (`beforeSubmit`)

`beforeSubmit` runs as soon as a submit starts. If it returns a promise, it runs in parallel with validation. Unexpected throws or rejected promises are treated as plugin bugs (sent to `onPluginError` while the submit continues).

To intentionally block a submit, return `refuse` (either directly or resolved from a promise). The form skips `onSubmit`, ends the submission as `"invalid"`, and passes that result to `onSubmitted`. Always attach an error first so the user knows what went wrong:

```ts
import { definePlugin, refuse } from "@lunarhue/forms-core/plugins";

export const captcha = definePlugin({
  name: "captcha",
  setup: (ctx) => ({
    async beforeSubmit() {
      try {
        const token = await fetchToken();
        ctx.write(() => ctx.store.root.at("token").setValue(token, { edited: false }));
        return undefined;
      } catch {
        ctx.store.root.setErrors({ message: "We couldn't check the form. Try again." });
        return refuse;
      }
    },
  }),
});
```

Returning `refuse` synchronously short-circuits any later plugins' `beforeSubmit` hooks; returning it asynchronously can't, since all `beforeSubmit` hooks start together. Note that if the form uses a custom `mapError`, any error your plugin sets should match the form's error shape.

## Reacting after a submit (`onSubmitted`)

`onSubmitted(submission, input)` runs when a submit completes. `input` is the snapshot read right after validation (the same `ctx.input` passed to `onSubmit`, including any edits made while async validation ran). It is defined whenever `onSubmit` ran (even if `onSubmit` ended `"invalid"` via `setErrors`) and `undefined` if validation or a plugin blocked the submit first. Submits aborted by `reset()` never reach `onSubmitted`.

If your plugin needs to advance the baseline after a save, call `ctx.baseline.move(path, value, keep)`. By default, arrays pair with their current items by index; pass a `keep` callback to either return `true` (preserve the previous baseline pairing) or return an explicit list of item keys, which is how `baselineOnSubmit` keeps array dirty flags accurate across in-flight edits.

## Starting values

To supply a form's starting values *before* the store initializes, define an `initialValue(currentValue, options)` hook. Return a replacement value, or `undefined` to keep the current one:

```ts
// Starts the form from a value shared by both server and client.
export const startFrom = definePlugin({
  name: "start",
  initialValue: (_value, start: Profile) => start,
});

const form = useForm(profile, { plugins: [startFrom(saved)] });
```

The store, its baseline, and its server snapshot all start from that value with no write records emitted, and the form starts clean (not dirty). If multiple plugins define `initialValue`, they chain in order so the last one wins.

Keep two things in mind:
- **Replaces wholesale:** `initialValue` replaces the starting value rather than deep-merging with schema defaults, though it receives those merged defaults as its first argument if you want to merge yourself.
- **Must match on server and client:** returning browser-only data (like `localStorage`) from `initialValue` will cause hydration mismatches. Read client-only storage in `onActive` with `ctx.write` instead, just like `persist`.

Parts don't have an `initialValue` hook. Instead, a part's `beforeWrite` runs once on attach with `cause: "attach"`, moving the baseline along with it if the field isn't dirty (which is how `masked` cleans initial values without marking the form dirty).
