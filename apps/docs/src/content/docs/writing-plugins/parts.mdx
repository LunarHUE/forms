A form-wide plugin is often too broad—a 20-character cap belongs on a note field, not on every string in your app. **Parts** let you target hooks to a specific place: a field type, a fieldset, or a single form definition. Try typing past 20 characters below.

## Standalone parts (no plugin required)

Most per-field behaviors don't need form-level state or a shared API. `@lunarhue/forms-core/plugins` exports three standalone part helpers that work without installing any plugin:

- **`transform<V>((value, write) => V | refuse)`** — cleans or normalizes values written to that path (including its initial value on attach).
- **`text<V>(display, afterInput?)`** — formats what text inputs display without changing the stored value (see [Display text](./meta#display-text)).
- **`observe<V>((value, ctx) => void)`** — runs on attach and after every batch that touches its path; use `ctx.write(...)` for side effects.

```ts
import { observe, transform } from "@lunarhue/forms-core/plugins";

// Only fits string fields.
export const capped = (max: number) => transform<string>((value) => value.slice(0, max));

// Auto-generates the slug whenever the title changes.
export const slugged = observe<Post>((post, ctx) => ctx.write(() => ctx.at("slug").setValue(slugify(post.title))));
```

The `V` type parameter constrains which fields can accept the part, so `defineField(NumberInput, capped(20))` is caught at compile time.

Need other hooks (like `onWrite` or `onBlur`)? Use `part<V>(hooks)` directly, or pass a callback receiving the part context—which gives you `ctx.value()` for the current value and `ctx.at(name)` for child handles:

```ts
import { part } from "@lunarhue/forms-core/plugins";

const logged = part<string>((ctx) => ({
  onWrite: () => console.log(ctx.path, ctx.value()),
}));
```

Standalone parts run after all plugin hooks and appear in `ctx.parts` under the name `"part"`.

## Plugin-backed parts

When a part needs to write plugin meta, coordinate with a form-level API, or require another plugin, define a `part` hook inside `definePlugin`. It runs once per attached path with that part's config and path context, and `part(plugin, config)` creates typed instances of it. (Our character limit below is simple enough for `transform`, but it illustrates the pattern cleanly:)

```ts
import type { Part } from "@lunarhue/forms-core";
import { definePlugin, part } from "@lunarhue/forms-core/plugins";

interface Limit {
  readonly max: number;
}

export const limit = definePlugin({
  name: "limit",
  part: (_ctx, { max }: Limit) => ({
    beforeWrite: (write) => (typeof write.value === "string" ? write.value.slice(0, max) : write.value),
  }),
});

// Fits string fields only.
export const limited = (max: number): Part<typeof limit, string> => part(limit, { max });
```

Consumers install `limit()` in `plugins` and attach `limited(...)` wherever needed. Annotating the return type as `Part<typeof limit, string>` enforces both compile-time checks: attaching `limited` to a non-string field fails, and using it on a form without `limit()` installed fails. (You can also pass the type arguments directly on `part<typeof limit, string>(limit, { max })`.)

## How and where parts attach

Every part—standalone or plugin-backed—plugs into the same three places: `defineField(NoteInput, limited(140))`, `forms.fieldset(Address, part)`, or `forms.define(config, part)`.

Inside a part's hooks, `ctx.path` is the stable path it attached to, and hooks only receive writes relevant to that path:
- A write *above* the path is walked down to it (and returning `refuse` cancels the whole parent write).
- A write *below* the path arrives as-is.
- If the field disappears (for example, when an array row is removed), its part hooks are torn down automatically.

When a part first attaches, its `beforeWrite` runs once with the existing value and `cause: "attach"`. Any transformed value is stored quietly with no write record, and the baseline moves with it if the field isn't dirty—so cleaning an initial value won't start the form dirty.

Timing depends on where the part lives: definition parts attach immediately when the store is created, field-type parts attach on first render, and fieldset parts attach on first `scope()` call. If the store doesn't have subscribers yet (such as during SSR), hooks initialize synchronously so their writes show up in the initial HTML; once subscribers exist, they initialize on a microtask so writes never fire mid-render.

One rule of thumb: always declare fieldsets with standalone parts at module scope next to `createForms`. Creating one after a store already exists without any hooked plugins throws [`parts:late`](/errors#core:parts:late) in development.
