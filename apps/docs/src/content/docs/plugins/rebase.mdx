Imagine a user is halfway through editing their profile when a fresher copy arrives from the server (a background refetch, a WebSocket update, or a save response). Replacing the form wholesale wipes out what they're typing, while ignoring the refresh leaves stale data in untouched fields.

`rebase` merges the two field by field. Try editing the name in the demo below, then click **Refresh**—your typed name stays put while the email picks up the server's update.

## Rebasing onto fresh data

Call `form.plugins.rebase(handle, incoming, resolve)` to move the baseline at `handle` to `incoming`. Any leaf whose current value already matches `incoming` simply advances its baseline. For every leaf that differs, your `resolve` callback chooses what happens:

```ts
const fresh = await fetchProfile();
form.plugins.rebase(form.root, fresh, (leaf) => (leaf.edited ? "keep" : "take"));
```

Each `leaf` gives you its `path`, current `value`, previous `baseline`, `incoming` value, and `edited` (`true` if the user has edited it). Return one of three outcomes:

- **`"keep"`** — preserve the user's current value (the field remains dirty against the new baseline).
- **`"take"`** — adopt the incoming server value.
- **`{ value }`** — write a custom merged value of your own.

## Protecting the currently focused field

There's a subtle edge case with `leaf.edited ? "keep" : "take"`: if the user clicked into a field and is about to type, `edited` is still `false`—so a background refresh could swap the value right under their cursor.

Pair `leaf.edited` with `isFocused(handle)` to protect whichever field currently has focus (including inputs nested inside custom components):

```ts framework=react
import { isFocused } from "@lunarhue/forms-react";

form.plugins.rebase(form.root, fresh, (leaf) => {
  const field = form.store.fieldAt(leaf.path);
  return leaf.edited || (field !== undefined && isFocused(field)) ? "keep" : "take";
});
```

```ts framework=solid
import { isFocused } from "@lunarhue/forms-solid";

form.plugins.rebase(form.root, fresh, (leaf) => {
  const field = form.store.fieldAt(leaf.path);
  return leaf.edited || (field !== undefined && isFocused(field)) ? "keep" : "take";
});
```

`isFocused` checks the elements registered via `field.ref` (the same ones `elementsOf` returns), so it works in production with zero extra setup. (By contrast, `fieldOf(document.activeElement)` only works in production if you called `trackElements()` up front, and it doesn't walk up ancestor elements inside custom components.)

If you have a custom composite input bound to an object field—like a date range over `{ start, end }`—its ref is registered on the parent object, so check the leaf's parent handle with `form.store.fieldAt(leaf.path.slice(0, -1))`.

## When to use `rebase` vs. `reset({ values })`

Use `rebase` when you want to **preserve** the user's edits while updating the baseline. When you want to **discard** edits and start fresh with new data—like after a save or when loading a different record—you don't need a plugin at all. Use `form.store.reset({ values })`:

```ts
const fresh = await fetchProfile();
form.store.reset({ values: fresh });
```

`reset({ values })` writes the new values and sets them as the new baseline in a single step. Just like `reset()`, it clears touched, edited, and error state, aborts any in-flight submit, and clears `history`. With [`dirty()`](./dirty), the form is immediately clean, a later `reset()` returns to these new values, and `reset({ to: "initial" })` still returns to the original defaults.

Avoid doing this with `setValue`: `setValue` leaves the baseline untouched, so the form stays dirty and `reset()` reverts to the old values.

## Return value and partial rebases

`rebase` returns `{ taken }`, listing the paths written via `"take"` or `{ value }`. Any validators that had already run on those fields re-run automatically, and listeners notify once after the entire rebase finishes.

You can pass any handle in the form—like `form.root.at("address")`—to rebase just that subtree. Passing a handle from a different form throws [`rebase:store`](/errors#core:rebase:store).

## How values and arrays are compared

When [`dirty()`](./dirty) is installed, `rebase` uses your form's dirty equality check (including any custom `equals` function). Without `dirty()`, it compares with `Object.is`, meaning two `Date` instances with the same timestamp count as different and go to `resolve`.

Plain objects are walked key by key. Arrays are walked item by item when their baseline keys and order still match and the incoming array has the same length; otherwise, the entire array is passed to `resolve` as a single leaf.

## Interaction with other plugins

Rebase updates aren't user edits: `history` won't record an undo step for them, and `masked` parts won't clean them, since the incoming data is already the server's baseline copy.
