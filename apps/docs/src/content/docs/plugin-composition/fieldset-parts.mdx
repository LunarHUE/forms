A fieldset can carry parts too. The billing fieldset below brings its own
rule: untick "Same as shipping" and the billing address appears.

## Rules on a fieldset

Pass parts after the schema, or after the type argument when there is no
schema. With a type argument, name the plugins the parts need as the second
one, by their factories:

```ts
const BillingFieldset = forms.fieldset<Billing, typeof rules>(
  ruled({ address: (billing) => ({ hidden: billing.sameAsShipping }) }),
);

const Billing = forms.fieldset(BillingSchema, ruled({ address: (billing) => ({ hidden: billing.sameAsShipping }) }));
```

Or give the value type to `ruled` and leave the fieldset's type arguments
out. The fieldset takes both from the part:

```ts
const BillingFieldset = forms.fieldset(ruled<Billing>({ address: (billing) => ({ hidden: billing.sameAsShipping }) }));
```

A fieldset's rules get the fieldset's value, not the form's, and name fields
below it.

Make a fieldset at module scope, next to `createForms`. A store made before a
fieldset whose parts need no plugin, such as `transform(...)`, can't run
those parts when its own plugins have no hooks. In development that throws
[`parts:late`](/errors#core:parts:late).

## Pinning with at()

A fieldset's parts attach at each field it is used on, the first time its
scope is read. A rule that matters before that, such as one on a step the
user hasn't reached, can be pinned on the definition with `at`:

```ts
const order = forms.define({ defaultValues, onSubmit }, BillingFieldset.at("billing"));
```

They then attach when the store is made. Reading the scope later doesn't
attach them twice.

`at` takes a field name, so a typo is a type error. A field type has the same
method for its parts: see [Parts on field components](./field-parts).
