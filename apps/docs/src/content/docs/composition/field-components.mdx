Wrapping every input in `<form.Field>` works fine when you're getting started, but once your app has more than a couple of forms, you'll want your own labeled inputs and selects wired up automatically.

If you register a field component on `createForms()`, every form built from it gets that component right on `form` (like `form.TextField`), taking a typed `name` prop instead of a manual `field` prop, still with no plugins needed.

## Registering your components

Write a regular component that accepts a `field: FieldApi<T>` prop (where `T` is the value type it edits), then pass it in `createForms({ fields: { ... } })`:

```tsx framework=react
import { createForms, type FieldApi, inputProps } from "@lunarhue/forms-react";

interface TextFieldProps {
  field: FieldApi<string>;
  label: string;
}

function TextField({ field, label }: TextFieldProps) {
  return (
    <label>
      {label}
      <input {...inputProps(field)} />
    </label>
  );
}

export const forms = createForms({ fields: { TextField } });
```

```tsx framework=solid
import { createForms, type FieldApi, inputProps } from "@lunarhue/forms-solid";

interface TextFieldProps {
  field: FieldApi<string>;
  label: string;
}

function TextField(props: TextFieldProps) {
  return (
    <label>
      {props.label}
      <input {...inputProps(props.field)} />
    </label>
  );
}

export const forms = createForms({ fields: { TextField } });
```

Create `forms` once in a shared module and import it wherever you define forms.

## Using registered components

Each registered component takes all of its own props (minus `field`), plus either:

- **`name`**: a dotted field path like `"address.city"`. TypeScript filters autocomplete to fields whose value type matches the component, so a `FieldApi<string>` component won't accept a number field (see [Typed names and handles](./typed-paths)).
- **`handle`**: a field handle from `form.root.at(...)` or an array row.

```tsx
<form.TextField name="name" label="Name" />
<form.NumberField name="age" label="Age" />
```

Registered components also accept the same `validate` prop as `form.Field`, attaching a validator while mounted and cleaning it up on unmount:

```tsx
<form.TextField name="name" label="Name" validate={(name) => (name ? undefined : { message: "Enter your name." })} />
```

## Supporting optional fields

A component typed with `FieldApi<string>` only accepts required string fields, because an optional field like `nickname?: string` can start out `undefined`. To let one component handle both required and optional fields, include `undefined` in its type:

```tsx framework=react
interface TextFieldProps {
  field: FieldApi<string | undefined>;
  label: string;
}

function TextField({ field, label }: TextFieldProps) {
  return (
    <label>
      {label}
      <input {...inputProps(field)} />
    </label>
  );
}
```

```tsx framework=solid
interface TextFieldProps {
  field: FieldApi<string | undefined>;
  label: string;
}

function TextField(props: TextFieldProps) {
  return (
    <label>
      {props.label}
      <input {...inputProps(props.field)} />
    </label>
  );
}
```

Now `<form.TextField />` works on both `name: string` and `nickname?: string`. The same pattern works for checkboxes (`FieldApi<boolean | undefined>`) and nullable fields (`FieldApi<string | null>`).

One small caveat: TypeScript won't stop a `FieldApi<string | undefined>` component from manually calling `field.setValue(undefined)` on a required string field. Relying on `inputProps` (or writing a value of the expected type) keeps things safe. `FieldApi<number>` has the same trade-off because an empty number input can hold `undefined`.

## Defining specialized field types

Sometimes you want several distinct field types backed by the same UI component, like a `PhoneField` or `CodeField` that both render `TextField`, but with different masks or behavior attached. `defineField(component, ...parts)` creates a reusable field type you can register right alongside plain components:

```ts
const NameField = defineField(TextField);

const forms = createForms({ fields: { TextField, NameField } });
```

On its own, `defineField(TextField)` behaves the same as `TextField`. Add parts like an input mask or text transform after the component so every field rendered with it gets that behavior automatically. See [Parts on field components](../plugin-composition/field-parts).

## What registering costs

Everything you pass to `createForms({ fields })` ships with every form built from that `forms` object. Bundlers drop unused exports, but they can't drop unused keys of an object passed to a function call. A login form that never renders `form.RichTextEditor` still bundles the editor, and a `MoneyField` made with `defineField(MoneyInput, masked(...))` brings its mask along too.

So register the small fields nearly every form uses, and leave the heavy or rare ones to the forms that need them:

```ts title="forms.ts"
export const forms = createForms({ fields: { TextField, Checkbox, Select } });
```

For a date picker, a rich text editor or a money input that only a few screens use, render it with `<form.Field>` in the module that needs it, so the import lives there:

```tsx framework=react
import { DatePicker } from "./DatePicker";

<form.Field name="dueDate">{(field) => <DatePicker field={field} label="Due" />}</form.Field>
```

```tsx framework=solid
import { DatePicker } from "./DatePicker";

<form.Field name="dueDate">{(field) => <DatePicker field={field} label="Due" />}</form.Field>
```

When a whole feature leans on those fields, give it its own `createForms` next to its routes. See [Bundling, plugins, and `/mini`](../best-practices/bundling-and-splitting) for that pattern.
